ChoreBoy Code Studio · feature proposal · 2 Nov 2026

CBCS Team Sync

Code collaboration for ChoreBoy projects using only what a shop already has: the station network, the shared disk on net1, and the FaxMail terminal's email. No GitHub, no internet, no new hardware.

Recommendation

Keep real git history inside CBCS (vendored pure-Python dulwich) and move changes as signed git bundles over two transports. Inside a shop, stations sync through a hub folder on net1's shared disk within seconds. Between shops, one hub mails bundles to the other through the FaxMail terminal, typically within minutes. Both transports carry the same bundle, so USB hand-off works too.

Nothing on the FaxMail terminal has to change. Everything runs in-process on CBCS's Python 3.9, using the standard library plus pure-Python dulwich, which matters because ChoreBoy blocks running git, ssh or any other program.

3 · Analysis

Reasoning from first principles

Strip collaboration down and five things remain. The constraints we found then decide how each must be built.

IdentityEveryone agrees which project this is.
HistoryWho changed what, and why.
ExchangeChanges move between copies.
MergeTwo people's changes combine safely.
AwarenessYou know when something arrived and who is working on what.
Between shops the only link is email: minutes of delay, roughly 15 MB per message, sometimes lost or duplicated.
So every exchange is one self-contained bundle. Sending it twice is harmless. No back-and-forth protocol.
ChoreBoy refuses to run git, ssh or any other program.
So everything runs inside CBCS on Python 3.9: the standard library, plus pure-Python dulwich to write genuine git history.
The share is a soft NFS mount with a 0.5 s timeout, and SQLite cannot be shared across machines on it.
So hub files never change once written: write to a temp file, fsync, rename, then check the hash on every read. One small pointer file changes, under a lock.
Station and terminal clocks drift. The terminal even restores its time from a file after a reboot.
So order comes from the change graph (each change names its parents), never from timestamps.
Anyone on the internet can email a shop's address.
So every bundle is signed with the project's shared key (HMAC-SHA256), and incoming changes wait for review before they touch your files.
The people using this are shop builders, not git users.
So there are two everyday actions: Save change and Sync. There are no branches to manage. Conflicts appear as side-by-side choices.
The FaxMail terminal is another company's production appliance.
So nothing on it is required. CBCS only reads mail files and writes outgoing ones. The mail hook stays optional.
A shop has several stations but one terminal and one mailbox.
So there are two levels: stations sync with their shop hub, and only hubs talk by mail. One mail per shop, not one per station.
4 · Design

Architecture

A transport-neutral core produces and consumes bundles. Adapters move bundles. The feature installs as app/features/team_sync/ through the existing FeatureSpec registry. History is a genuine git repository written by dulwich, behind one CBCS interface so nothing above it uses git terms.

Writing to the hub safely

1. write objects (temp → fsync → rename)
2. take lease: mkdir cbcs/lease/  (EEXIST = someone else)
   stale after 60 s without heartbeat → break it
3. re-read refs/heads/main
   if it moved: fetch, merge locally, go to 1
4. update refs/heads/main  (dulwich: .lock file + rename)
5. remove cbcs/lease/
reads: git object ids are hashes; re-verify, retry on I/O error
5 · Format

Data and wire format

The mail format copies the shape of IntellaQuote's IQ-UPDATES/1, which already works through these terminals: a plain-text header block in the body, the payload as an attachment. Readable by a person, parseable by CBCS.

5b · Format decision · decided: dulwich 0.24.10

Real git, or our own format?

The format of the history is the one choice that is expensive to change later. Every saved change, every bundle and every shop's history is written in it. Transports, merge and the Team panel can all be replaced. The format cannot, without migrating every customer's history.

Git's object format brings things a home-grown one never will. Any git tool can read it, RockSolid can fetch a shop's bundle with plain git fetch, a GitHub mirror is easy, and the model has 20 years of proof. So the long-term answer is to store history as genuine git. What remains open is who writes it.

Why the freeze is acceptable. We use dulwich offline only: objects, packs and bundles. None of its network code is used. The only outside input it parses is a bundle from email, and CBCS checks the project signature first, so only bundles from members ever reach it. The lab already has a FreeCAD 1.1 image running Python 3.11 (ChoreBoyExp), so a ChoreBoy update may lift the freeze. That is unconfirmed for customer boxes.

What stays ours either way: merge, the sync and mail layers, signing, and the Team panel. dulwich sits behind one interface, and users never see git words.

6 · Flows

How a change travels

  1. 0 s
    Mary clicks Save change on net2CBCS records the new file versions and her note in her local store.
  2. +0.2 s
    Push to the shop hubNew objects go to net1's share, then the tip moves under the lease. A few KB for a typical edit.
  3. ≤ 15 s
    Joe's CBCS on net1 notices the tip movedIt polls one small file. With the LAN link added later, it hears a nudge in under a second.
  4. + review
    Joe sees "Mary saved 1 change"He opens the diff and accepts. Files he has not touched update. Overlaps go to the merge view.

About 15 seconds from save to notice.

Sent during
  1. 0 s
    Shop A hub gets Mary's changeSame as the same-shop flow.
  2. +5 s
    The station on mail duty writes an outgoing mailA folder in .Mails/default/out/ with .lock, message, bundle, then the lock is removed. If the terminal is off, it waits safely on the share.
  3. ≤ 15 s
    Shop A's terminal sends itcompile_mail.sh loops every 15 s, hands it to Postfix and files it under Sent.
  4. ≤ 3 min
    Shop B's terminal fetches itgetmail on the cron cadence, then writes zip_in/<ts>!.zip to Shop B's share.
  5. ≤ 30 s
    Shop B's mail-duty station imports itReads the zip without moving it, checks the signature, adds the changes to Shop B's hub as "incoming from Shop A".
  6. ≤ 15 s
    Clair sees "Shop A sent 1 change"She reviews and accepts. Shop B's hub then mails back a short have so Shop A knows it arrived.

Typically under 5 minutes by day.

Worst cases come from the terminals' cron schedule, read on the live terminal. Internet delivery time between the two upwardmail mailboxes is not measured yet.

  1. base
    Both start from the same changeThe graph knows their common ancestor, so CBCS can compare three versions instead of two.
  2. edits
    Mary edits lines 10–14, Joe edits lines 40–52 of invoice.pyDifferent regions merge automatically into a new change with two parents.
  3. overlap
    Both changed line 12The merge view shows Mine, Theirs and the original side by side. Pick one, combine, or edit by hand.
  4. forms
    Both changed invoice.uiDesigner forms and binary files are chosen whole, with a preview of each, because a line merge of XML can break a form.
  5. done
    Nothing is lostEvery version stays in history and can be restored, including the one not chosen.

8 · Delivery

Roadmap

Each phase ships something useful on its own and ends with a test on the cbfarm (a floor or a shop with fault injection) before it reaches a customer.

P0change history
Save change, history, diff, restore. Local only.
  • Vendor dulwich 0.24.10 and typing_extensions into the cp39 bundle. One history interface over them.
  • Team panel with history and diff. Restore any version.
  • Already useful for one person: named checkpoints that never expire.
Gate: unit tests for history and three-way merge on recorded edit pairs, git fsck --strict on every repo the tests produce, Python 3.9 compatible.
P1between shops · first
Shops share a project through FaxMail.
  • One station per shop shares the project. Its own history is the shop's copy until the hub arrives.
  • Invites with a shared key, membership, key rotation.
  • out/ writer, zip_in/inbox reader (read only), signature check, incoming review, merge view.
  • Have and want replies, resend, 10 MiB parts. Export and import a bundle file (USB).
Gate: two leased shops exchanging bundles through their twins with mail faults (drop, duplicate, reorder). Then one real round trip on the shop terminal with your OK. Measure the provider's real size cap.
P2shop hub
Stations in one shop share a project.
  • Create and join a hub on net1's share. Locate the share on net1 and on carts.
  • Lease lock, tip pointer, polling, presence.
  • Mail moves from the single station to the hub, with a leader lease for mail duty.
Gate: floor lease with net1 and two carts saving at the same time, with the NFS link dropped mid-write. No lost or torn change.
P3optional
LAN live link.
  • UDP "tip moved" nudge, so same-shop notice drops from 15 s to under 1 s.
  • Follow mode: watch what a teammate is doing.
P4optional
Bridges to RockSolid.
  • Export history to git (fast-import stream) so RockSolid can mirror a project to GitHub.
  • A RockSolid relay mailbox as a member: support, backups and fewer mails for larger teams.

Decisions

Answers recorded 2 Nov 2026.

Q1 · decided
Who collaborates first?

Between shops Mail between shops is now P1. The shop hub follows in P2.

Q2 · decided
Must history be real git?

Real git via dulwich 0.24.10 Proven on a confined ChoreBoy cart, with real git reading its bundles. See section 5b.

Q3 · decided

No terminal changes CBCS reads and writes mail files only. Sync mail shows in the shop inbox with a clear "no action needed" note.

Q4 · decided

Save-and-sync Overlaps go to the merge view. Live editing is out of scope.
