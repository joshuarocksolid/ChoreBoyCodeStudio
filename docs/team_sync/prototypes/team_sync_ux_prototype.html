Team Sync Prototype

Four ways the everyday Team Sync workflow could look inside CBCS. Each one is a different bet on where collaboration lives in the editor. Step through one day between two shops, switch between the four setups, and use the explanations below to compare them.

The story: Sam at Maple Ridge built an invoice app and shares it with Ana at Cedar Hollow. Changes travel as signed git bundles by email through each shop's FaxMail terminal, so nothing is instant: a change takes a few minutes by day. People, shops and code are examples. Nothing here touches real data.

    How each setup works

    Four setups, four bets

    All four share the same engine, the same dialogs for sharing, joining and combining, and the same tree letters (M changed, A new, ↓ incoming, ! needs your call). What differs is where your team's work lives day to day.

    What stays the same

    Share dialog

    Who to invite, an optional message, and the project's size. Vendor folders and caches are left out automatically. Sending builds the git history, a project key and a signed invite.

    Invite dialog

    Shows who invited you and that the invite was verified. You pick a folder and open the project. The invite email also stays in FaxMail.

    Review dialog

    Note, changed files and the diff, built on CBCS's existing diff view. Your files don't change until you press Accept, and every accept leaves a restore point.

    Combine dialog

    Everything that doesn't clash is combined automatically. For a line both people changed, you pick Yours, Theirs or Both. Forms (.ui) are picked whole.

    Explorer letters

    M changed since you last sent, A new file, ↓ incoming change waiting for you, ! a line that needs your call.

    Status bar

    A "Team:" segment next to Run and Project: Up to date, 3 to send, Queued, Sent, Delivered, 1 from Sam, or Terminal offline. In setup D it opens a popover.

    Recommendation

    C as the home, D's signals everywhere else

    Use the Thread (C) as the one Team view, and add Ambient's (D) toolbar Send button, editor bar and clickable status segment. Keep A's file list inside the composer so you always see what goes out.

    Why: between shops nothing is instant, so the work reads best as a conversation with clear delivery states, and a thread is exactly that. People spend nearly all their time in the editor, so new work should meet them on the file they're looking at instead of waiting in a panel. One Team view still gives history, notes and team settings an obvious home, which D alone lacks. B makes delivery easy to understand, but it turns code into mail and splits history across tabs. A is the most familiar to programmers but hides the delays and leaves no room for notes. When stations in the same shop can sync (phase 2), they join the same thread with faster ticks, so nothing has to be redesigned.

    Decisions · recorded 2 Nov 2026

    What was decided

    Direction: Thread + ambient. Saving: inside Send, with Save Only. Incoming: always review before anything applies. Alerts: badge, status bar and file bar, plus a toast popup when something arrives.

    The options considered are kept below for reference. Round two (diffs, combining, power tools) is in "Team Sync Power Tools".

    1 · Direction

    • Thread + ambient (C with D's signals)
    • A · Changes
    • B · Mailroom
    • D · Ambient only

    Recommended: Thread + ambient.

    2 · When a change is saved

    • Inside Send, with a "Save only" option for checkpoints
    • A separate Save step, then send one or more later
    • Automatically on every file save

    Recommended: inside Send. One verb to learn, and history stays readable.

    3 · Incoming changes

    • Always wait for Accept
    • Apply automatically when nothing clashes, with Undo

    Recommended: always wait for Accept. It matches the security design and nobody's files change by surprise.

    4 · How loud an arrival is

    • Badge, status bar, and a bar on any open file it touches
    • All of that plus a popup toast

    Recommended: no toast. Arrivals happen a few times a day and shouldn't interrupt typing.

    Not in this prototype yet

    Still to design

    • Adding or removing a teammate, and what happens to the project key when someone leaves.
    • A large change that goes out as several emails ("2 of 3 parts arrived").
    • A message that claims to be from the team but fails the signature check.
    • Saving and opening a bundle on USB when there's no terminal.
    • Undoing an accept from the toast or from history.
    • Stations in the same shop syncing through net1's shared folder (phase 2).
